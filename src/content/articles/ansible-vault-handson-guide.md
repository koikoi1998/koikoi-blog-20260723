## はじめに

- **この記事で得られること**: データベースのパスワードやAPIキーといった機密情報を、Playbookや変数ファイルにプレーンテキストのまま書き、そのままGitリポジトリにコミットしてしまう、という実務で非常によくあるアンチパターンを、**Ansible Vault**を使って解決します。機密情報を含むファイルを暗号化した状態でバージョン管理し、実行時にだけ復号する、という安全な運用を体験します。
- **対象読者**: Ansible Vaultという名前は聞いたことがあるが、実際に使ったことがなく、機密情報をどう扱えばよいか迷ったことがある方を想定しています。
- **読むのにかかる想定時間**: 約20分(実際に構築しながら進める場合は40分程度を見込んでください)

## そもそも、なぜこの問題が起きるのか

Ansibleの変数ファイル(`group_vars`や`host_vars`)は、通常、他のPlaybookのコードと一緒にGitリポジトリで管理されます。**ここに、データベースの接続パスワードのような機密情報を、プレーンテキストのまま書いてしまうと、そのGitリポジトリの閲覧権限を持つ人全員が、その機密情報を読めてしまいます。** さらに厄介なのは、一度Gitの履歴にコミットされてしまうと、後から該当の行を削除しても、過去のコミット履歴を遡れば、その機密情報を読み取れてしまう、という点です。

## ハンズオン手順

### Step 1: 機密情報を含む変数ファイルを暗号化する

データベースのパスワードを含む、変数ファイルを作成します。**このハンズオンでは、実際にデータベースサーバーを構築するわけではありません。** 「実務でPlaybookが扱うことになる、典型的な機密情報の一例」として、データベースのパスワードという設定値を、あくまで題材として使っているだけです。ここで重要なのは、この値の中身そのものではなく、これから行う「機密情報を含む変数ファイルを暗号化する」という一連の手順です。

```bash
cat > db_secrets.yml << 'EOF'
db_password: "SuperSecretP@ssw0rd"
EOF
```

このファイルを、Ansible Vaultで暗号化します。

```bash
ansible-vault encrypt db_secrets.yml
```

**実行すると、暗号化に使うパスワードの入力を求められます。** このパスワードを覚えておいてください。今後、このファイルを復号したり、編集したりする際に、毎回このパスワードが必要になります。

### Step 2: 暗号化されたファイルの中身を確認する

`cat db_secrets.yml`を実行して、ファイルの中身を確認してください。**中身が、`$ANSIBLE_VAULT`から始まる、意味の読み取れない暗号文になっている**ことが確認できます。この状態であれば、このファイルをそのままGitリポジトリにコミットしても、機密情報が漏洩することはありません。

### Step 3: Vaultパスワードを使ってPlaybookを実行する

この暗号化された変数ファイルを読み込むPlaybookを実行する際は、Vaultパスワードを追加で指定する必要があります。

```bash
ansible-playbook -i inventory.ini site.yml --ask-vault-pass
```

**`--ask-vault-pass`を指定すると、実行時にVaultパスワードの入力を求められ、そのパスワードで一時的に復号したうえで、Playbookが実行されます。** 復号された内容がディスク上に平文で残ることはありません。毎回手入力するのが煩わしい場合は、Vaultパスワードをファイルに保存しておき、`--vault-password-file`オプションでそのファイルを指定することもできます(ただし、そのファイル自体をGitリポジトリに含めないよう、`.gitignore`への追加を忘れないでください)。

### Step 4: 暗号化されたファイルの内容を編集する

暗号化されたファイルの内容を後から変更したい場合、一度手動で復号してから再暗号化する、という手間のかかる手順は不要です。

```bash
ansible-vault edit db_secrets.yml
```

**このコマンドは、Vaultパスワードの入力を求めたうえで、一時的に復号した内容をエディタで開き、保存すると自動的に再暗号化する**、という一連の流れを1つのコマンドにまとめてくれます。

## プロが見ている視点(上位1%の理解)

### 「暗号化されたファイル」と「されていないファイル」を、Gitリポジトリで安全に共存させる設計

実務では、Playbook全体を丸ごと暗号化するのではなく、**機密情報を含む変数だけを、専用の暗号化されたファイル(`vault.yml`のような名前にすることが多い)に切り出し、それ以外の通常のPlaybookやタスク定義は、暗号化せずにそのままバージョン管理する**、という設計が一般的です。これにより、暗号化されていない大部分のコードは、通常通りGitの差分レビューが可能なまま、機密情報だけを安全に保護できます。

この設計でよく登場するのが、`group_vars/all/vault.yml`という配置です。`group_vars`は、[dev/staging/prodを1つのPlaybookで安全に使い分けるハンズオン](/articles/ansible-environments-handson-guide)で詳しく扱っている、インベントリのグループごとに変数を管理する仕組みで、`group_vars/all/`は「すべてのホストに共通する変数」を置く、その中でも特別な場所です。この`group_vars/all/`の中に、暗号化された`vault.yml`(機密情報)と、暗号化されていない`vars.yml`(それ以外の変数)を両方置き、`vars.yml`の中から`vault.yml`で定義した変数を参照する、という組み合わせがよく使われます。

### vault-idを使った、複数の暗号化パスワードの使い分け

より高度な使い方として、`ansible-vault`には、**vault-id**という仕組みがあります。これは、たとえば「開発環境用の暗号化パスワード」と「本番環境用の暗号化パスワード」を別々に管理し、同じリポジトリの中で、異なるパスワードで暗号化された複数のファイルを使い分けられるようにする仕組みです。

```bash
ansible-vault encrypt --vault-id prod@prompt prod_secrets.yml
ansible-playbook site.yml --vault-id prod@prompt
```

**この仕組みがあることで、開発環境のVaultパスワードを知っている人が、誤って本番環境の機密情報まで復号できてしまう、という事故を防ぐことができます。** チームの規模が大きくなり、環境ごとにアクセスできる人を分けたい場合には、この`vault-id`による分離が実務上重要になります。

## よくある誤解・つまずきポイント

- **誤解1: 「Ansible Vaultで暗号化したファイルを編集するには、一度手動で復号してから再度暗号化する必要がある」**
  `ansible-vault edit`コマンドを使えば、復号・編集・再暗号化を1つのコマンドで完結できます。
- **誤解2: 「Vaultパスワードさえ知っていれば、どの暗号化ファイルでも復号できる」**
  `vault-id`を使って複数のパスワードを使い分けている場合、そのファイルに対応する正しいパスワードを知らなければ復号できません。
- **誤解3: 「暗号化したファイルは、Gitの差分レビューができなくなる」**
  暗号化されたファイル自体の差分レビューはできませんが、機密情報を含まない、それ以外の大部分のPlaybookのコードは、通常通り差分レビューが可能です。

## 障害・トラブルシューティングの視点

1. **`ansible-playbook`の実行時に、Vaultパスワードの入力を求められない**: そのファイルが実際に暗号化されているか、`cat`コマンドで`$ANSIBLE_VAULT`から始まっているかを確認してください。
2. **Vaultパスワードを入力したのに復号に失敗する**: `vault-id`を使い分けている場合、そのファイルの暗号化に使われたパスワードと、指定したvault-idが一致しているかを確認してください。
3. **`--vault-password-file`で指定したファイルが誤ってGitにコミットされてしまった**: 直ちにそのファイルの内容を変更し(Vaultパスワード自体をローテーションし)、Gitの履歴からも削除する対応を検討してください。

## まとめ

- Ansible Vaultを使うと、機密情報を含む変数ファイルを暗号化した状態でバージョン管理できます。
- `ansible-vault edit`コマンドで、復号・編集・再暗号化を1つの手順で行えます。
- 機密情報だけを専用の暗号化ファイルに切り出し、それ以外のコードは暗号化しないという設計が実務では一般的です。
- `vault-id`を使うと、環境ごとに異なる暗号化パスワードを使い分けられます。

**今日から意識すべきこと**
1. Playbookに機密情報を書く必要が出たら、プレーンテキストのまま書く前に、必ずAnsible Vaultでの暗号化を検討しましょう。
2. `--vault-password-file`を使う場合は、そのファイル自体を`.gitignore`に追加することを忘れないようにしましょう。
