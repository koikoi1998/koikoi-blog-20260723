## はじめに

- **この記事で得られること**: [DNSサーバーの基礎](/articles/dns-server-fundamentals-guide)で触れた**DNS増幅攻撃**(DNS Amplification Attack)について、小さな問い合わせが、どれだけ大きな応答を引き出せてしまうのかを、実際に`dig`で計測します。そのうえで、BINDの**レスポンスレートリミティング**(RRL、Response Rate Limiting)という防御機能を有効化し、同一の送信元からの大量の問い合わせに対して、応答そのものが自動的に間引かれる様子を確認します。
- **対象読者**: DNS増幅攻撃という言葉は知っているが、実際にどの程度の増幅が起きるのか、そしてそれをどう防ぐのかを、自分の手で確認したことがない方を想定しています。**このハンズオンは、自分が管理する検証環境の防御力を高めるための、教育・防御目的のものです。実運用中の他者の環境に対して、許可なくこの手順を実行しないでください。送信元IPアドレスを偽装する行為(スプーフィング)は、このハンズオンでは一切扱いません。**
- **読むのにかかる想定時間**: 約30分

## ハンズオン手順

### Step 1: 大きな応答を返す問い合わせを用意する

[BINDでDNSサーバーを構築するハンズオン](/articles/dns-server-handson-guide)の`lab.example.test`ゾーンに、意図的にサイズの大きいTXTレコードを追加します。

```
big  IN  TXT  "AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA...(400文字程度まで繰り返す)"
```

```bash
sudo named-checkzone lab.example.test /etc/bind/db.lab.example.test
sudo systemctl restart bind9
```

### Step 2: 問い合わせと応答のサイズを比較し、増幅率を計測する

`dig`に`+stats`を付けて実行し、実際に送信したクエリのサイズと、受信した応答のサイズを比較します。

```bash
dig @<サーバーのIP> big.lab.example.test TXT +stats
```

出力の末尾にある`MSG SIZE  rcvd`と、送信したクエリのおおよそのサイズ(数十バイト程度)を比較してください。**クエリ自体は数十バイト程度の小さなUDPパケットであるにもかかわらず、応答は数百バイトに達しているはずです。** これが**増幅率**であり、この例では数倍程度ですが、実際の攻撃では、より応答サイズの大きいレコード(DNSSECの署名を含むDNSKEYレコードなど)を悪用することで、数十倍の増幅率に達することもあります。

**この小さな問い合わせを、送信元IPアドレスを標的のIPアドレスに偽装して大量に送りつけることで、標的に対して、送信した問い合わせの何倍ものトラフィックを送りつけることができてしまう、というのがDNS増幅攻撃の正体です。** このハンズオンでは、このスプーフィング自体は行いません。

### Step 3: レスポンスレートリミティング(RRL)を有効化する

`named.conf.options`に、RRLの設定を追加します。

```
options {
    rate-limit {
        responses-per-second 5;
        window 5;
    };
};
```

**`responses-per-second 5`は、同一の問い合わせパターンに対して、同一の送信元へ、1秒あたり5回までしか応答しないという設定です。** それを超える分は、応答が意図的に間引かれます。

```bash
sudo named-checkconf
sudo systemctl restart bind9
```

### Step 4: 大量の問い合わせを送り、応答が間引かれることを確認する

自分自身のマシンから(送信元を偽装せず)、同じ問い合わせを短時間に連続して送信します。

```bash
for i in $(seq 1 20); do dig @<サーバーのIP> big.lab.example.test TXT +noall +stats; done
```

`journalctl`または`rndc stats`で、RRLの動作ログを確認します。

```bash
sudo rndc stats
sudo tail -n 20 /var/cache/bind/named.stats
```

**設定した閾値(1秒あたり5回)を超えた問い合わせに対して、応答が`Dropped`(破棄)または`Slipped`(一部だけ切り詰めた応答)として処理されている記録が確認できます。** 自分自身への問い合わせであっても、RRLは送信元アドレスと問い合わせ内容の組み合わせだけを見て、機械的にレートを制限していることが分かります。

## プロが見ている視点(上位1%の理解)

### RRLは「攻撃者への応答」を減らすことで、加害を抑制する仕組み

RRLの本質的な狙いは、**自分のDNSサーバーが受ける負荷を軽減することではなく、自分のサーバーが、DNS増幅攻撃の踏み台として、第三者(スプーフィングされた標的)へ送りつけてしまうトラフィックの量そのものを減らす**ことにあります。攻撃者からの問い合わせ自体を完全にブロックするのではなく、**同一パターンの問い合わせへの応答頻度を、一定の閾値までに絞り込む**ことで、仮に自分のサーバーが踏み台にされてしまった場合でも、標的が受け取る増幅されたトラフィックの総量を、大幅に抑制できます。

### `Slip`という、正規の利用者への影響を最小化する仕組み

RRLには、応答を完全に`Drop`(破棄)する設定と、一部の応答だけ`Slip`(TCPへの切り替えを促す、切り詰めた応答)として返す設定があります。**正規の利用者が、たまたま閾値を超える頻度で問い合わせを送ってしまった場合、完全に応答を破棄してしまうと、正規の名前解決まで失敗してしまいます。** `Slip`は、UDPでの応答を意図的に破損させることで、クライアント側に「UDPでは正しい応答が得られなかったので、信頼性の高いTCPで再試行してほしい」という挙動を促します。**攻撃者が送信元を偽装している場合、TCPでの再試行(3ウェイハンドシェイクが必要)は事実上不可能なため、攻撃トラフィックだけを効果的に抑制しつつ、正規の利用者への影響を最小限に抑える**、という工夫がここに込められています。

## よくある誤解・つまずきポイント

- **誤解1: 「RRLを有効にすれば、DNS増幅攻撃自体を完全に防げる」**
  RRLは、自分のサーバーが踏み台にされた場合の加害量を抑制する仕組みであり、増幅攻撃という手法自体を根絶するものではありません。
- **誤解2: 「RRLは、問い合わせ自体をすべてブロックする機能である」**
  RRLは問い合わせの受付自体は拒否せず、応答の頻度だけを制限します。
- **誤解3: 「増幅率は、どのレコードタイプでも同じである」**
  TXTレコードやDNSKEYレコードのように、応答サイズが大きくなりやすいレコードタイプほど、増幅率は高くなります。

## 障害・トラブルシューティングの視点

1. **正規の利用者から、名前解決が不安定だという報告がある**: RRLの閾値(`responses-per-second`)が、正規の利用パターンに対して厳しすぎないかを確認します。
2. **RRLを有効にしたのに、ログに記録が出ない**: `named.conf.options`の`rate-limit`ブロックが正しく読み込まれているか、`named-checkconf`で構文エラーがないかを確認します。
3. **自分のサーバーが、増幅攻撃の踏み台として悪用されていないか調査したい**: 外部から到達可能な状態で、再帰機能や大きな応答を返すレコードが、不必要に公開されていないかを確認します。

## まとめ

- DNSは、小さな問い合わせから、それより大きな応答を引き出せてしまう、増幅という性質を構造的に持っています。
- DNS増幅攻撃は、この性質と送信元IPアドレスの偽装(スプーフィング)を組み合わせて、標的へ増幅されたトラフィックを送りつける攻撃です。
- レスポンスレートリミティング(RRL)は、同一パターンの問い合わせへの応答頻度を制限することで、自分のサーバーが踏み台にされた場合の加害量を抑制します。
- `Slip`という部分的な応答破損の仕組みにより、正規の利用者への影響を抑えながら、攻撃トラフィックを効果的に抑制できます。

**今日から意識すべきこと**
1. 外部に公開しているDNSサーバーには、RRLの設定を有効にすることを検討しましょう。
2. 再帰機能や、応答サイズの大きいレコードを、不必要に外部へ公開していないかを定期的に点検しましょう。
