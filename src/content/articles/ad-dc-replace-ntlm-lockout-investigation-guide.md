- **この記事で得られること**: [旧DCから新DCへのAD移行(リプレース)ハンズオン](/articles/ad-migration-handson-guide)で扱った移行作業の中で、実務上よく遭遇する、「**新しいDCへ昇格した直後、Administratorアカウントでログインできなくなる**」という事象を、**実際にその事象へ遭遇した人の立場から、エラーを1つずつ調査していく過程**を追体験します。手順をなぞるハンズオンとは異なり、「**原因が分からない状態から、調査によって原因を突き止める**」という、実務のトラブルシューティングそのものの形式を取ります。
- **対象読者**: 新しいDCへ昇格した直後に、Administratorアカウントでログインできなくなる事象に遭遇し、原因や対処法が分からず困っている方、あるいはこれから同様のDCリプレース作業を行う予定の方を想定しています。
- **重要な注意**: 本記事の原因分析は、[NTLM認証の仕組み](/articles/ad-ntlm-mechanism-guide)・[IAKerbとローカルKDCの仕組み](/articles/ad-iakerb-localkdc-guide)で整理した仕組みと、Microsoft社の公開情報・コミュニティでの報告例を根拠にしていますが、Microsoft社が原因を公式に確定させた文書は見当たらず、**現時点で最も裏付けの強い仮説**として提示しています。実際の環境で同様の事象に遭遇した場合は、本記事の調査手順を参考にしつつ、必ず自分の環境での事象と突き合わせて確認してください。

## 事象:新DC昇格後の再起動後、Administratorでログインできなくなった

**AWS上で、旧DCから新DC(WindowsServer 2025)へのリプレースを検証していたときに、次の事象が発生しました。**

1. 新サーバーをDCへ昇格させると、自動的に再起動が発生した。
2. 再起動後、踏み台サーバーから新DCへRDP接続を試みた。
3. **RDP接続のポップアップ(資格情報の入力画面)では、認証エラーは一切表示されなかった。**
4. **しかし、そのまま新DCのデスクトップ画面へは遷移せず、新DC自身のWindowsログイン画面で、パスワードが拒否されてしまった。**
5. 旧DCへログインし、Administratorアカウントのパスワードを再設定したところ、新DCへのRDP接続が正常に行えるようになった。

**この事象を、手順書を知らない状態から、どうやって調査していくか**を、順を追って見ていきます。

## 調査ステップ1:どの段階で失敗しているかを、イベントログから切り分ける

[Kerberos認証の仕組み](/articles/ad-kerberos-guide#障害トラブルシューティングの視点)で扱った通り、Kerberos関連の障害は、**どの段階で失敗しているか**を、イベントIDを軸に切り分けます。新DC自身のセキュリティログを確認します。

```powershell
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4768,4771} -MaxEvents 20 |
    Select-Object TimeCreated, Id, Message | Format-List
```

**実行結果(該当部分、イメージ):**

```
TimeCreated : 2026-10-05 10:15:32
Id          : 4771
Message     : Kerberos pre-authentication failed.
              Account Information: Administrator
              Failure Code: 0x17 (KDC_ERR_ETYPE_NOTSUPP)
```

**イベントID 4771(事前認証失敗)が記録されており、失敗コードは`0x17`(`KDC_ERR_ETYPE_NOTSUPP`、「サポートされていない暗号方式」)でした。** これは、**KDCが、クライアントから提示された暗号方式(etype)に対応する鍵を、このアカウントに対して持っていない**ことを意味します。クライアント側は、おそらくAES(より新しい、現在の既定の暗号方式)で事前認証を試みたものの、**KDC側に、このアカウントのAESキーが存在しない**ために、この段階で拒否されていると推測できます。

<details>
<summary>RDPのポップアップでは、なぜエラーが表示されなかったのか</summary>

RDP接続時の資格情報入力ポップアップ(NLA、Network Level Authentication)は、**接続を開始するための、ネットワークレベルでの認証**です。ここで一旦何らかの形で認証が受け付けられたように見えても、**実際にデスクトップ画面へ遷移するための、Windows自身のログオン処理(Winlogon)は、別の、より厳密な認証のやり取りです。** 本記事で確認したイベントID 4771は、このWinlogonの裏側で行われているKerberos認証の失敗を記録したものです。**「ポップアップでエラーが出なかった=認証が完全に成功した」ではない**、という点が、この事象の分かりにくさの一因になっています。

</details>

## 調査ステップ2:このアカウントに、本当にAESキーが存在しないのかを確認する

イベントログから立てた仮説を、別の角度から確認します。Microsoft社の公開ドキュメントには、「**組み込みのAdministratorアカウントは、WindowsServer 2008以降のDC上でパスワードが変更されていない限り、AESキーを持たない**」という、重要な記述があります。

```powershell
# このドメインのAdministratorアカウントの、パスワード最終変更日時を確認する
Get-ADUser -Identity Administrator -Properties PasswordLastSet, whenCreated |
    Select-Object Name, PasswordLastSet, whenCreated
```

**実行結果(イメージ):**

```
Name          PasswordLastSet       whenCreated
----          ---------------       -----------
Administrator 2019-04-02 09:12:00   2019-04-02 09:10:15
```

**このドメインのAdministratorアカウントのパスワードが、ドメイン作成時から一度も変更されていない**ことが分かりました。**パスワードが設定された、まさにそのタイミングで、AES・RC4それぞれのキーが計算されて保存されます。** つまり、「KDCサービスが起動していたかどうか」そのものではなく、「**このアカウントのパスワードが、最後に設定された時点で、どのような暗号方式のキーが計算されたか**」が、本当の分岐点だったと考えられます。

<details>
<summary>最初の仮説(KDCサービスが起動していなかったため)との違い</summary>

今回の調査では、**「新DC昇格時にKDCサービスがまだ起動していなかったため、AESキーが作られなかった」という仮説は、裏付けが取れませんでした。** AES・RC4のキー計算は、KDCサービス(Windowsサービスとして動いている、Kerberosの実行時プロセス)そのものではなく、**パスワード変更処理のパイプライン(LSA・NTDSの内部処理)によって行われる**ため、KDCサービスが起動しているかどうかとは、直接の関係がありません。むしろ、「**このアカウントのパスワードが、いつ、どのDC上で最後に設定されたか**」という、パスワードの履歴そのものが、鍵を握っていました。

</details>

## 調査ステップ3:パスワード再設定で解決した理由を確認する

旧DCでAdministratorのパスワードを再設定した後、新DCへのRDP接続が成功するようになりました。これは、**パスワードの再設定によって、AES・RC4両方のキーが新たに計算され、このドメインのすべてのDC(新DCを含む)へレプリケーションされた**ためだと説明できます。

```powershell
# パスワード再設定後、レプリケーションが新DCへ届いているかを確認する
repadmin /showrepl <新DCのホスト名>
```

**実行結果(該当部分、イメージ):**

```
最終成功時刻: 2026-10-05 10:45:12 (エラーなし)
```

**レプリケーションが正常に完了していることを確認できれば、新DC側でもAES対応のキーが利用可能になっている**はずです。

## プロが見ている視点(上位1%の理解)

### この事象の、本当の教訓:「古いパスワードは、古い暗号方式を抱えたまま」

この事象から得られる最も重要な教訓は、「**アカウントが古くから存在し、パスワードが一度も変更されていない場合、そのアカウントの資格情報は、そのパスワードが最後に設定された時点の暗号方式のまま、何年も、何世代のOSアップグレードをまたいでも、そのまま引き継がれ続ける**」という点です。ドメインのOSやDCをいくら新しいバージョンへアップグレードしても、**既存アカウントの資格情報そのものは、自動的に新しい暗号方式へ"書き換わる"わけではありません。** パスワードが実際に変更されたタイミングだけが、資格情報を更新する機会になります。これは、[RAID5のパリティがデータを複製せず、必要最小限の情報だけを持つ](/articles/raid5-parity-guide)話とは対照的に、**「古いデータは、明示的な再生成の機会がない限り、古いまま残り続ける」という、移行やアップグレード全般に通底するリスク**です。

### AWS上で、新規にWindowsServer 2025のDCを構築する場合はどうなるか

ここで、本記事の調査を踏まえて、**まったく新しい(既存DCが存在しない)フォレスト・ドメインを、WindowsServer 2025で新規構築する場合**を考えます。**この場合、Administratorアカウントのパスワードは、フォレスト作成ウィザード(`Install-ADDSForest`)の実行時に、まさにそのWindowsServer 2025上で設定されます。** 本記事の調査結果に基づけば、**この時点でAES・RC4両方のキーが計算されるはずであり、今回のような事象は、通常は発生しません。** 今回の事象が実際に問題となるのは、「**既存の、古いドメインを、新しいDCへ段階的に移行する**」という、まさに今回のようなリプレースのシナリオに限られます。

## よくある誤解・つまずきポイント

- **誤解1: 「RDP接続のポップアップでエラーが出なければ、認証は完全に成功している」**
  RDP接続時のポップアップは、接続を開始するための認証であり、実際にデスクトップへ遷移するためのWindows自身のログオン処理は、別のやり取りです。
- **誤解2: 「KDCサービスが起動していないと、Kerberosのキー自体が計算されない」**
  AES・RC4のキー計算は、パスワード変更処理のパイプラインによって行われ、KDCサービス(Windowsサービスとしての実行プロセス)の起動状態とは、直接の関係がありません。
- **誤解3: 「OSやDCを新しいバージョンへアップグレードすれば、既存アカウントの資格情報も自動的に新しい暗号方式へ更新される」**
  既存アカウントの資格情報は、パスワードが実際に変更されない限り、以前の暗号方式のまま残り続けます。

## 障害・トラブルシューティングの視点

1. **新DC昇格後、特定のアカウントだけログインできない**: イベントID 4771の失敗コードを確認し、`KDC_ERR_ETYPE_NOTSUPP`であれば、そのアカウントのパスワード最終変更日時を確認します。
2. **パスワードを再設定しても、まだログインできない**: `repadmin /showrepl`で、新DCへのレプリケーションが正常に完了しているかを確認します。
3. **新規にフォレストを構築したのに、同様の事象が発生した**: 何らかの手段(バックアップからの復元、別ドメインからの移行など)で、Administratorアカウントのパスワード履歴が、新しいフォレストの作成時点より前にさかのぼっていないかを確認します。

### 予防策・恒久対策

- **DCのリプレース作業を行う前に、使用する予定の特権アカウントのパスワードを、現行のDC上で明示的に再設定しておく**ことを、作業手順に組み込みます。事後対応ではなく、事前の予防策として扱うべきです。
- 既存ドメインの特権アカウントについて、パスワード最終変更日時を定期的に棚卸しし、長期間変更されていないアカウントがないかを確認します。

## まとめ

- 新DC昇格直後にAdministratorでログインできなくなる事象は、RDPのポップアップ認証とWindows自身のログオン処理(Kerberos認証)が、別々のやり取りであることに関係しています。
- イベントID 4771・失敗コード`KDC_ERR_ETYPE_NOTSUPP`は、KDCがクライアント提示の暗号方式に対応するキーを、このアカウントに対して持っていないことを示します。
- AES・RC4のキーは、パスワードが実際に設定された時点で計算されるため、長期間パスワードが変更されていないアカウントは、古い暗号方式のキーしか持っていない可能性があります。
- 新規にフォレストをWindowsServer 2025で構築する場合、この事象は通常発生しません。既存ドメインのリプレース作業に特有の事象です。

**今日から意識すべきこと**
1. DCのリプレース作業を行う前に、使用予定の特権アカウントのパスワードを、必ず事前に再設定しておきましょう。
2. 「ポップアップでエラーが出なかった」だけで、認証が完全に成功したと判断しないようにしましょう。
