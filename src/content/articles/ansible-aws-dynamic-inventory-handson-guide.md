## はじめに

- **この記事で得られること**: [Ansibleで複数サーバーへの設定投入を自動化するハンズオン](/articles/ansible-handson-guide)では、`inventory.ini`に管理対象サーバーのIPアドレスを手書きしました。しかし、クラウド環境では、インスタンスを起動・停止するたびにIPアドレスが変わったり、オートスケーリングで台数そのものが増減したりします。この記事では、静的なファイルを手で書き換える代わりに、**Ansibleがそのつど最新のEC2インスタンス一覧を、AWSから直接動的に取得する**、動的インベントリを構築します。
- **対象読者**: `inventory.ini`にIPアドレスを手書きする方法しか知らず、クラウド環境でのインベントリ管理に悩んだことがある方を想定しています。
- **読むのにかかる想定時間**: 約20分(実際に構築しながら進める場合は45分程度を見込んでください)

## 前提知識

## そもそも、なぜ静的なInventoryファイルでは対応できないのか

`inventory.ini`にサーバーのIPアドレスを手書きするやり方は、オンプレミス環境のように、サーバーのIPアドレスが固定されている場合には問題になりません。しかし、AWSのEC2インスタンスは、**再起動するたびにパブリックIPアドレスが変わる**ことが一般的です(Elastic IPを使わない限り)。**インスタンスを増やしたり減らしたりするたびに、`inventory.ini`を手作業で書き換え続けるという運用は、クラウド環境の俊敏性そのものを損なってしまいます。**

## ハンズオン手順

### Step 1: 動的インベントリプラグインをインストールする

AWS用のコレクションをインストールします。

```bash
ansible-galaxy collection install amazon.aws
pip install boto3 botocore
```

### Step 2: AWS用の設定ファイルを作成する

固定のIPアドレスを書く代わりに、「AWSから動的に取得する」という設定だけを書いたYAMLファイルを作成します。

```yaml
# aws_ec2.yml
plugin: amazon.aws.aws_ec2
regions:
  - ap-northeast-1
filters:
  instance-state-name: running
keyed_groups:
  - key: tags.Role
    prefix: role
```

**このファイルには、IPアドレスやサーバー名が1つも書かれていない点に注目してください。** `plugin: amazon.aws.aws_ec2`という宣言が、「実行のたびにAWS APIへ問い合わせて、最新のインスタンス一覧を取得する」という動作そのものを指示しています。

### Step 3: 動的に取得されたインベントリを確認する

このファイルを指定して、実際にAWS上のインスタンス一覧を取得できることを確認します。

```bash
ansible-inventory -i aws_ec2.yml --list
```

**タグ・インスタンスID・パブリックIP・プライベートIPなど、AWS側の情報がそのままインベントリとして表示される**ことを確認してください。この時点では、まだ`inventory.ini`のような静的なファイルは一切使っていません。

### Step 4: タグでグループ化してPlaybookを実行する

`keyed_groups`の設定により、EC2インスタンスに付けた`Role`タグの値をもとに、Ansibleのグループが自動的に作られます。`Role`タグに`webserver`と設定したインスタンスだけを対象に、Playbookを実行してみましょう。

```bash
ansible-playbook -i aws_ec2.yml site.yml --limit role_webserver
```

**手作業でインベントリファイルにグループを定義することなく、AWSコンソール上でタグを1つ付け替えるだけで、そのインスタンスが自動的に正しいAnsibleグループに分類される**ようになります。

## プロが見ている視点(上位1%の理解)

### 動的インベントリと、IAMロールを組み合わせる意味

このハンズオンのAWS APIへの問い合わせは、`control`ノード自体がAWS上のEC2インスタンスであり、[IAMロールでEC2にアクセスキーを一切持たせないハンズオン](/articles/aws-iam-role-handson-guide)で扱った、**IAMロールがアタッチされていれば、アクセスキーを一切設定することなく成立します。** 動的インベントリプラグインは、内部的にAWSのSDK(boto3)を使ってAPIを呼び出しており、そのSDKは、環境変数・設定ファイル・そしてIAMロールという順番で認証情報を探しに行きます。**「Ansible Vaultで暗号化した固定のアクセスキーを使う」という選択肢もありますが、`control`ノード自体がEC2上にあるなら、IAMロールを使う方が、そもそも管理すべき認証情報自体をゼロにできる、より優れた選択です。**

### 動的インベントリが実現する、実務上の本当の価値

動的インベントリの本当の価値は、単に「IPアドレスを手で書かなくて済む」という利便性にとどまりません。**オートスケーリンググループによってインスタンスの台数が自動的に増減するような環境では、そもそも「対象サーバーの正確な一覧」を人間が把握し続けること自体が現実的ではありません。** 動的インベントリを使えば、Playbookを実行するその瞬間に実際に稼働しているインスタンスだけが、自動的に対象になります。これは、[gMSAでパスワード管理から解放されるハンズオン](/articles/ad-gmsa-handson-guide)で扱った「人間が管理しなければならない状態を減らす」という設計思想の、Ansibleにおける具体的な実践だと言えます。

## よくある誤解・つまずきポイント

- **誤解1: 「動的インベントリを使うには、`inventory.ini`のような静的ファイルとの併用が必須である」**
  動的インベントリだけで完結させることもできますし、複数のインベントリソース(静的ファイル+動的インベントリ)を組み合わせることもできます。
- **誤解2: 「動的インベントリを使うと、実行のたびにグループを手動で指定し直す必要がある」**
  `keyed_groups`の設定により、AWS側のタグに応じて、Ansibleのグループが自動的に生成されます。
- **誤解3: 「動的インベントリを使うには、アクセスキーの設定が必ず必要である」**
  `control`ノードにIAMロールがアタッチされていれば、アクセスキーの設定は不要です。

## 障害・トラブルシューティングの視点

1. **`ansible-inventory --list`を実行しても、インスタンスが1台も表示されない**: `regions`の指定が正しいか、`filters`の条件(`instance-state-name: running`など)に合致するインスタンスが実際に存在するかを確認してください。
2. **認証エラーになる**: `control`ノードにIAMロールが正しくアタッチされているか、そのロールにEC2の一覧取得権限(`ec2:DescribeInstances`など)が含まれているかを確認してください。
3. **タグでグループ化されない**: EC2インスタンス側に、指定したキー名(`Role`など)のタグが正しく設定されているかを確認してください。

## まとめ

- 動的インベントリを使うと、固定のIPアドレスを書いた静的なインベントリファイルが不要になります。
- `amazon.aws.aws_ec2`プラグインは、実行のたびにAWS APIへ問い合わせて最新のインスタンス一覧を取得します。
- `keyed_groups`を使うと、AWS側のタグに応じてAnsibleのグループが自動的に生成されます。
- `control`ノードがEC2上にあり、IAMロールがアタッチされていれば、アクセスキーの設定は不要です。

**今日から意識すべきこと**
1. クラウド環境でAnsibleを使う場合は、まず静的インベントリではなく動的インベントリで実現できないかを検討しましょう。
2. EC2インスタンスには、Ansibleのグループ化に使えるタグ(役割・環境など)を、作成時から一貫して付ける運用にしましょう。
