## 基礎から徹底解説

### リダイレクト:出力先・入力元を切り替える仕組み

Linuxのコマンドは、既定では「標準出力」という、画面に文字を表示する経路に結果を出力します。**リダイレクト**は、この出力先(または入力元)を、画面ではなく別の場所(ファイルなど)に切り替える仕組みです。

| 記号 | 意味 |
|---|---|
| `>` | 標準出力をファイルへ書き込む(ファイルが既に存在する場合は、中身を上書きする) |
| `>>` | 標準出力をファイルへ追記する(既存の内容は消えず、末尾に追加される) |
| `<` | ファイルの中身を、コマンドの標準入力として渡す |

```bash
echo "Hello" > greeting.txt
cat greeting.txt
```

**`echo`コマンドの結果は、本来なら画面に表示されるはずですが、`>`によって画面ではなく`greeting.txt`というファイルへ書き込まれます。**`>`を`>>`に変えれば、実行するたびに追記されていき、`>`のように毎回上書きされることはありません。

### ヒアドキュメント:複数行のテキストをまとめて渡す仕組み

`<`は、既存の1つのファイルの中身を渡す仕組みですが、**ヒアドキュメント**(`<<`)は、これから続けて入力する複数行のテキストそのものを、その場でコマンドへ渡す仕組みです。

```bash
cat > db_secrets.yml << 'EOF'
db_user: admin
db_password: SecretP@ss123
EOF
```

この構文は、次のように読み解けます。

1. `cat > db_secrets.yml`: `cat`コマンドの出力を`db_secrets.yml`というファイルへ書き込む(リダイレクト)
2. `<< 'EOF'`: 「ここから、`EOF`という文字列だけの行が現れるまでを、`cat`への入力として扱う」という宣言
3. 2行目・3行目: `cat`への実際の入力内容(コマンドではなく、ただのテキストデータ)
4. 最後の`EOF`: 入力の終わりを示す、終端の目印

`cat`は、本来ファイルの中身を表示するためのコマンドですが、ここでは入力元も出力先も指定されていないため、標準入力からそのまま受け取った内容を、標準出力へそのまま流す、という動作になります。**その標準入力が、ヒアドキュメントによって「これから続く複数行のテキスト」に差し替えられ、その標準出力が、リダイレクトによって`db_secrets.yml`というファイルに差し替えられている**、という2段構えの仕組みが、この1行の中に同時に成立しています。

<details>
<summary>終端の目印は「EOF」でなければならないのか</summary>

いいえ、`EOF`という文字列自体に特別な意味はありません。慣習的に「End Of File」の略として`EOF`が使われているだけで、`END`や`STOP`など、任意の文字列を使うことができます。ただし、本文の中にたまたま同じ文字列の行が登場すると、そこで誤って終端と判定されてしまうため、本文中に登場しなさそうな、一意性の高い文字列を選ぶことが実務上の注意点です。

</details>

### シングルクォートとダブルクォートで囲む場合の違い

`<< 'EOF'`のように、`EOF`をシングルクォートで囲むかどうかで、動作が変わります。

```bash
name="World"
cat << EOF
Hello, $name
EOF
```

```bash
cat << 'EOF'
Hello, $name
EOF
```

**`EOF`をクォートで囲まない場合、ヒアドキュメントの中身にある`$name`のような変数は、シェルによって実際の値に展開されます。** 1つ目の例の出力は`Hello, World`です。一方、**シングルクォートで囲んだ場合は、変数展開が一切行われず、`$name`という文字列がそのまま出力されます。** 2つ目の例の出力は`Hello, $name`のままです。設定ファイルのテンプレートなど、`$`という文字自体をそのままファイルに書き込みたい場合は、シングルクォートで囲む書き方が必須になります。

## プロが見ている視点(上位1%の理解)

### なぜハンズオン記事でnanoではなくヒアドキュメントが使われるのか

このブログのハンズオン記事では、`nano`でファイルを対話的に編集する手順と、ヒアドキュメントでファイルを一括作成する手順の、両方が登場します。この使い分けには理由があります。**ヒアドキュメントは、ファイルの内容がコマンド自体の中に文字列として埋め込まれているため、その手順を実行するだけで、誰でも寸分違わず同じ内容のファイルを再現できます。** 一方`nano`のような対話的エディタは、人間が画面を見ながら打ち込む前提のため、手順書には「このように入力してください」という説明はできても、実行そのものを自動化することはできません。Ansibleのようなツールを使わずに、シェルスクリプトだけで環境構築を自動化したい場面では、ヒアドキュメントが標準的に使われます。

## よくある誤解・つまずきポイント

- **誤解1: 「`>`と`>>`は同じ意味で、書きやすい方を使えばよい」**
  `>`は既存の内容を上書きし、`>>`は末尾に追記します。ログファイルへの追記のつもりで`>`を使ってしまうと、過去の内容がすべて消えてしまう事故につながります。
- **誤解2: 「ヒアドキュメントの終端の目印は、必ず`EOF`と書かなければならない」**
  `EOF`は単なる慣習であり、任意の文字列を使えます。ただし本文中に登場しない、一意な文字列を選ぶことが重要です。
- **誤解3: 「ヒアドキュメントの中では、変数は常に展開される」**
  終端の目印をシングルクォートで囲むと、変数展開は一切行われなくなります。

## 障害・トラブルシューティングの視点

1. **ヒアドキュメントを実行しても、コマンドプロンプトに戻ってこない**: 終端の目印(`EOF`など)の行が、正しく単独の行として存在するか確認してください。前後に余計な空白文字が入っていると、終端として認識されないことがあります。
2. **ファイルの中身に変数名がそのまま`$name`と書き込まれてしまう**: 終端の目印をシングルクォートで囲んでいないか確認してください。変数展開させたい場合は、クォートなしの`<< EOF`にします。
3. **`>`で上書きするつもりが、意図せず内容が追記されている**: `>`ではなく`>>`を使っていないか確認してください。

## まとめ

- `>`は上書き、`>>`は追記という、リダイレクトの基本的な違いです。
- ヒアドキュメント(`<<`)は、複数行のテキストをその場でコマンドの標準入力として渡す仕組みです。
- 終端の目印(`EOF`など)は慣習的な文字列にすぎず、任意の文字列を選べます。
- 終端の目印をシングルクォートで囲むと変数展開が無効化され、`$`をそのまま書き込みたい場合に使います。

**今日から意識すべきこと**
1. `>`を使う前に、それが上書きしてよい操作なのか、`>>`で追記すべき操作なのかを、一呼吸置いて確認しましょう。
2. ヒアドキュメントの中に`$`を含む内容を書く場合は、変数展開させたいかどうかで、クォートの有無を意識的に選びましょう。
