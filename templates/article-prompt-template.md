# インフラ技術ブログ 記事作成プロンプト（テンプレート）

> 使い方: 新しいチャットを開いたら、このテンプレート全文をコピペし、
> `【テーマ】` と `【語り口】` の2箇所だけ書き換えて送信してください。
> それ以外の構成・深さの指定は固定なので触らなくてOKです。

---

## プロンプト本文（ここからコピー）

以下の条件に厳密に従って、自分のブログサイトに公開できるインフラエンジニア向け技術ブログ記事をMarkdown形式で作成してください。

### 1. 記事の基本情報
- テーマ: 【ここに今回扱いたい技術テーマを記入。例: 「AWSのVPCとサブネット設計」「KubernetesのService/Ingressの仕組み」「TCPの3ウェイハンドシェイクと再送制御」など】
- 語り口: 【「会話形式（初心者とベテランの対話）」「解説形式（体系的な講義スタイル）」のいずれかを指定。未指定の場合は解説形式で作成】
- 想定読者: インフラエンジニアとして就業しているが、当該テーマについては基礎レベル〜業務でなんとなく使っている程度の理解の人。ただし過去に本シリーズの記事を読んでいる前提で書いてよく、毎回初心者向けの説明をゼロからやり直す必要はない（前提知識は該当する過去記事へのリンクを埋め込むことで担保する）。
- 目標とする理解の到達点: AWS・Google・Microsoftなど外資トップ企業に在籍するインフラエンジニアの上位1%相当が持つレベルの理解（表面的な使い方だけでなく、内部動作・設計思想・トレードオフ・障害時の挙動まで説明できる状態）。ここが本シリーズで最も重視するポイントであり、初心者向けの丁寧さよりも深掘りの量を優先すること。

### 2. 記事の必須構成（この見出し構成・順序を厳守すること）

```
---
title: "（テーマが一目でわかる具体的なタイトル）"
description: "（検索結果やOGPに使う1〜2文の要約）"
series: "（シリーズ名。例: idrac / network / api。新規シリーズなら新しい名前を決めてよい）"
order: （同じseries内での読む順番。数値）
tags: ["（関連タグを3〜5個、小文字英数字）"]
emoji: "（内容に合う絵文字1つ、任意）"
pubDate: 2026-07-23
draft: true
---

## はじめに
- この記事で得られること
- 対象読者（レベル感を明記）
- 読むのにかかる想定時間
- [『上位1%』シリーズ 全記事ガイド](/sitemap) へのリンクを1行。関連する既存記事があれば、そこへのリンクも埋め込む

## 前提知識
- この記事を読む前に知っておくべき用語・概念を箇条書きで整理
- 過去記事で詳しく扱っている場合はその記事へのリンクを埋め込み、本文では簡潔な要約にとどめる

## 全体像をつかむ
- 詳細に入る前に、テーマの全体像を図解（Mermaid記法）または比喩を使って直感的に説明
- 「結局何のためにあるものなのか」を一言で言い切る

## 基礎から徹底解説
- テーマを構成要素に分解し、要素ごとに見出しを立てて解説
- 各要素について「何をするものか」だけでなく「なぜそう設計されているのか」まで踏み込む
- 必要に応じてMermaid図・比較表・コードブロック・コマンド例を使う
- 公式ドキュメントの記載事項は必ず一次情報ベースで正確に説明する
- 主題から外れる補足説明は`<details><summary>見出し</summary>`ブロックに収め、本文の主軸を読みやすく保つ

## プロが見ている視点（上位1%の理解）
- 初心者向け解説では省略されがちな内部動作・パフォーマンス特性・スケーラビリティへの影響
- 設計上のトレードオフ（コスト・可用性・セキュリティ・運用負荷など）
- 大規模環境やマルチリージョン・マルチアカウント運用における考慮点
- 実際にAWS/Google等のドキュメントやベストプラクティスで言及されている注意点

## よくある誤解・つまずきポイント
- 初心者が陥りがちな誤解を具体的に列挙し、なぜそれが誤解なのかを説明
- 実務でありがちな設定ミス・アンチパターン

## 障害・トラブルシューティングの視点
- このテーマに関連して実際に発生しうる障害パターン
- 障害発生時の切り分け方・調査コマンド・ログの見方
- 恒久対策や予防策

## まとめ
- 記事全体の要点を箇条書きで再整理
- 「今日から意識すべきこと」を1〜2個に絞って提示

## 参考文献
- 公式ドキュメントなど一次情報のリンクを明記（記事内で言及した情報の裏付けとなるもの）
```

### 3. 執筆時の注意事項
- 一次情報（AWS公式ドキュメント、Google Cloud公式ドキュメント、RFC等）を必要に応じて調査し、正確性を最優先すること。不明確な場合は検索して確認すること。
- 表面的な「使い方」の説明で終わらせず、必ず「なぜそうなっているか」「内部で何が起きているか」まで掘り下げること。ハンズオン（実機・仮想環境での実習手順）は本シリーズの対象外とし、深掘りした説明そのものに紙面を使うこと。
- 図解が理解を助ける箇所ではMermaid記法の図を積極的に使うこと。
- 比較・対比が理解を助ける箇所では表形式を使うこと。
- 冗長な前置きは避け、読者が実務にすぐ活かせる密度の高い内容にすること。
- コードブロックやコマンドは実際に動作する正確なものを記載すること。
- 会話形式を選んだ場合でも、内容の網羅性・技術的深さは解説形式と同等を維持すること（対話はあくまで理解を助けるための演出であり、内容を薄めてはいけない）。
- 内容が広がりすぎる場合は無理に1記事に収めず、別記事に分割してリンクでつなぐこと（分割した場合は`src/pages/sitemap.md`にも記事を追記する）。

## 運用メモ（自分用）

- 新しいテーマのたびに新規チャットを開き、上記プロンプトの2箇所（テーマ／語り口）だけ書き換えて投げる。
- 構成やレベル感を変えたくなったら、このファイル自体を編集してテンプレートを更新する。
- 初稿ができたら`src/content/articles/<slug>.md`として保存する。`slug`は英数字とハイフンのみ。
- 新しいテーマ（シリーズ）を始める場合は、以下も合わせて行う。
  1. `src/content/config.ts`の`series`のenumに新しいシリーズ名を追加する
  2. `feedback/<slug>/`フォルダを作成する
  3. `src/pages/sitemap.md`にシリーズと記事へのリンクを追記する
- `npm run dev`でローカルプレビューしながら執筆・確認する。
